# Mini Chat — Telegram × GREEN-API

Минимальный React-клиент для тестового задания: вход с данными GREEN-API, создание чата по номеру телефона, отправка и получение текста. Next.js App Router, TypeScript, React, TanStack Query, CSS Modules.

**Почему Telegram, а не MAX.** Задание допускает Telegram как альтернативу. Я живу в Минске, аккаунта в MAX у меня нет, и я им не пользовался — поэтому не смог бы проверить реальную доставку и ответ получателя. Telegram-инстанс GREEN-API использует те же методы (`SendMessage`, `receiveNotification` / `deleteNotification`), так что перенос на MAX сводится к замене инстанса, текстов интерфейса и инструкции по подключению.

## Локальный запуск

Нужен Node.js 22+ и npm.

```sh
npm ci
npm run dev
```

Откройте http://127.0.0.1:3000.

```sh
npm test         # проверки API, маршрутизации и обработки уведомлений
npm run build   # production-сборка Next.js в .next/
npm run start   # запуск production-сборки
npm run typecheck # проверка TypeScript
npm run check    # TypeScript + Oxlint + Oxfmt + тесты
npm run format   # форматирование исходников
```

## Подключение с нуля

1. Зарегистрируйтесь в https://console.green-api.com/ и создайте **Telegram**-инстанс. Условия тарифа и доступность уточняйте в кабинете.
2. Авторизуйте инстанс: получите QR-код в кабинете и отсканируйте его через Telegram → Настройки → Устройства → Подключить устройство. Дождитесь состояния `authorized`.
3. В настройках инстанса очистите `webhookUrl`, включите `incomingWebhook = yes` (входящие сообщения), `outgoingWebhook = yes` (статусы отправки) и `stateWebhook = yes` (состояние инстанса). После изменения настроек подождите около минуты.
4. Скопируйте `apiUrl`, `idInstance`, `apiTokenInstance` из кабинета в форму приложения. Токен бота от BotFather здесь не используется.
5. Нажмите «Начать общение», затем кнопку с карандашом «Новый чат» слева и введите номер получателя с кодом страны.
6. Отправьте текст. Получатель отвечает в своём Telegram; ответ появится в открытом чате.

Поиск номера зависит от настроек приватности получателя. Приложение использует `checkAccount` и сохраняет полученный Telegram `chatId`, поэтому ответ не создаёт отдельный чат.

## Архитектура: Next.js + адаптированный FSD

Next.js отвечает за маршрутизацию и сборку. Клиентская граница `ChatScreen` подключает интерактивный чат; состояние чатов и учётные данные хранятся только в памяти вкладки. Запросы к GREEN-API идут через Route Handler `src/app/api/green/[...path]/route.ts` — тонкий прокси без собственной логики, базы данных и серверной авторизации. Он нужен, чтобы не зависеть от CORS и не светить токен в адресах запросов браузера.

Маршруты, API, продуктовый модуль и общий слой разделены. Это доменная организация с фичами, а не каноническая иерархия слоёв FSD.

```text
src/
  app/                        # Next.js App Router и композиция экрана
    layout.tsx                # metadata, глобальные стили, Query-провайдер
    page.tsx                  # маршрут /
    chat/                     # ChatScreen и интеграционный тест
    api/green/[...path]/      # прокси к GREEN-API (Route Handler)
  api/                        # транспорт и контракты GREEN-API
    query-provider.tsx        # отдельный QueryClient на экземпляр приложения
    instance/
    contacts/
    messages/
    notifications/
  telegram/                   # продуктовый модуль чата
    components/               # список, переписка, сообщения, рабочая область
    features/
      connect-instance/       # подключение и проверка учётных данных
      create-chat/            # поиск получателя и создание чата
      send-message/           # отправка сообщения и поле ввода (message-composer)
    hooks/                    # сессия, состояние чатов, координация экрана
    services/                 # последовательная обработка очереди уведомлений
    types/                    # модели чата и сообщения
    const/                    # константы чата
    utils/                    # чистые преобразования состояния
  common/
    components/               # общие UI-компоненты
    hooks/                    # общие React-хуки
    utils/                    # форматирование, нормализация, async, test helpers
    styles/                   # общие стили контролов
    analytics/                # Яндекс Метрика (включается переменной окружения)
```

`app` собирает экран из функциональных модулей. `telegram` использует `api` и `common`; обратных импортов нет. `common` не знает о Telegram, маршрутах и API приложения. `api` не зависит от `telegram` или `app`. Новые фичи держат свои компоненты, хуки и сервисы рядом; общая для чата логика находится на уровне `telegram`.

Для импортов между модулями используются алиасы `@/api`, `@/telegram/...`, `@/common/...`. Локальные импорты внутри модуля могут быть относительными. Фичи имеют публичный `index.ts`; общего barrel-файла всего домена нет, чтобы внутренние модули не импортировали собственный домен через него.

### Как проходит запрос

`Компонент → хук сценария → сервис (если нужны проверки/преобразования) → API-модуль → HTTP-клиент`.

Пример подключения:

- `telegram/features/connect-instance/components/connect-instance-form/index.tsx` — поля и отображение состояния.
- `telegram/features/connect-instance/hooks/connect-instance.ts` — `useMutation`, отправка формы, `isConnecting`, ошибка.
- `telegram/features/connect-instance/services/connect-instance.ts` — проверка состояния и настроек инстанса.
- `api/instance/index.ts` — именованные методы `getState` и `getSettings`.
- `api/client.ts` — адрес запроса, таймаут, HTTP-ошибки и JSON. Повторов запросов здесь нет.

У каждой API-группы (`instance`, `contacts`, `messages`, `notifications`) свои `index.ts` и `types.ts` (в `instance` также вынесен `queries.ts` для TanStack Query). Ответы проверяются Zod-схемами, описанными по документации GREEN-API; типы выводятся из этих схем. Генератор Orval пока не используется. Ошибки `checkAccount` при HTTP 200 отделены от результата «аккаунт не найден».

`telegram/services/connection.ts` владеет жизненным циклом соединения: запуском, остановкой, проверкой инстанса и восстановлением. React-хук `useConnection` подписывается на его состояние через `useSyncExternalStore`; эффект только запускает соединение и останавливает его при размонтировании. `telegram/services/poll-notifications.ts` выполняет чтение очереди уведомлений. Этот процесс требует последовательного получения и подтверждения, поэтому не заменён обычным `useQuery` с интервалом. `telegram/utils/chat.ts` содержит чистые преобразования состояния.

TanStack Query управляет состоянием мутаций и запросом состояния инстанса при восстановлении через `QueryClient.fetchQuery`. Настройки запроса находятся в `api/instance/queries.ts`; `signal` библиотеки передаётся в API-метод и транспорт. Ключ запроса содержит случайный идентификатор соединения, а не токен; при завершении соединения запрос отменяется и удаляется из кеша. У очереди отдельный контроллер, поскольку она выполняет последовательный процесс получения и подтверждения. `Providers` создаёт отдельный QueryClient для приложения, отключает автоматические повторы и ожидание восстановления сети для мутаций. Для команд форм отмена при размонтировании остаётся в `useAbortableTask`: мутации не получают автоматическую отмену query. Отмена HTTP-запроса не откатывает отправку на сервере. Ошибки транспорта стандартизированы; ошибки операций отображаются рядом с соответствующей формой. Данные чатов и черновики остаются локальным React-состоянием.

### Правила читаемости

- Типы имеют префикс `T`, состояния — `is…`, обработчики — `handle…`.
- API-контракты лежат рядом с запросами; константы — в `const.ts` своего модуля.
- Чистые общие функции находятся в тематических `common/utils/date`, `phone`, `errors`; сервисы выполняют побочные эффекты.
- Фичи экспортируют свой публичный API через `index.ts`; компонент находится в `components/имя/index.tsx`. Хуки находятся в `hooks/`, файлы называются без префикса `use-`, экспорт — `use…`.
- Компоненты используют соседний `s.module.css`; общие визуальные классы — `common/styles/controls.module.css`. Глобально остаются reset, типографика и базовое оформление HTML-контролов.
- Oxlint и Oxfmt закрепляют именованные экспорты, function expressions, фигурные скобки, одинарные кавычки, табы и группы импортов. Конфиги JSON совместимы с Node.js 22.14.

Тесты находятся рядом с проверяемым кодом (`*.test.ts`, `*.test.tsx`). Vitest использует Vite только как внутреннюю тестовую зависимость: приложение собирает Next.js. Проверяются транспорт, маршрутизация, дедупликация, сохранение адресата при смене чата и работа polling при повторном запуске эффектов в Strict Mode.

Прокси принимает учётные данные в заголовках `x-green-api-url`, `x-green-id-instance`, `x-green-api-token` и проверяет их по тем же правилам, что и форма входа: только `https://*.green-api.com`, числовой `idInstance`, имя метода из латинских букв. Наружу передаются только `Content-Type` и `Accept`; cookie и прочие заголовки клиента до GREEN-API не доходят. Поэтому прокси нельзя использовать как открытый релей на произвольные адреса.

Получение: `receiveNotification` → обработка → `deleteNotification`. Корректные уведомления неподдерживаемых типов также подтверждаются, чтобы не блокировать очередь. Повреждённые ответы останавливают чтение без подтверждения уведомления; сообщение об ошибке предлагает проверить совместимость API перед повторным подключением. Повторные доставки текста не создают дубликаты. Отключение отменяет запросы. Ошибки отправки не вызывают автоматическую повторную отправку; черновик сохраняется, поскольку после сетевого сбоя результат отправки может быть неизвестен.

## Ограничения первой версии

- Только текст; файлы и полная история Telegram не загружаются.
- Токен, чаты и сообщения хранятся **только в памяти вкладки**. Перезагрузка или выход очищают их; уже подтверждённые уведомления повторно из очереди не придут.
- Держите один экземпляр приложения на инстанс: другие потребители HTTP-очереди могут забирать уведомления.
- Для работы нужен Node.js-сервер Next.js (`npm run dev` или `npm run start`): запросы идут через встроенный прокси, статический экспорт не поддерживается. Токен проходит через сервер приложения транзитом и нигде не сохраняется и не логируется.
- Статус «В очереди» означает принятие API, а не доставку адресату. Для дальнейших статусов нужен `outgoingWebhook`.
- Google Fonts используется для Manrope; при недоступности сети применяется системный шрифт.
- Реальную доставку можно проверить только с подключённым Telegram-инстансом и вторым получателем. Автоматические тесты используют подменённые ответы API.

## Ручная проверка

Подключиться → создать чат по номеру → отправить текст → ответить из Telegram → убедиться, что ответ в том же чате → проверить второй чат, ошибочный номер и выход. Не включайте реальные токены в репозиторий или скриншоты.

## Аналитика (Яндекс Метрика)

Метрика с Вебвизором подключается, только если задан `NEXT_PUBLIC_YM_ID` (см. `.env.example`). Без переменной скрипт не загружается и данные никуда не отправляются, в том числе при локальном запуске.

- Поля ввода и область чатов помечены классами `ym-hide-content ym-disable-keys`: Вебвизор не записывает токен, номера телефонов и тексты сообщений.
- Цели (`reachGoal`) передают только название события: `connect_success`, `connect_error`, `chat_created`, `chat_create_error`, `message_sent`, `message_send_error`, `message_received`, `logout`.

## Восстановление подключения

Состояние авторизации Telegram отделено от состояния HTTP-очереди. При временном сетевом сбое очередь повторяет запросы с задержкой; отправка и создание новых чатов приостановлены. Читать переписку и редактировать черновик можно.

Уведомление `stateInstanceChanged` блокирует отправку, если инстанс больше не `authorized`. Пустой успешный ответ очереди не восстанавливает авторизацию. Ошибки доступа 401/403 при получении, отправке или поиске контакта останавливают обработку.

Кнопка «Проверить подключение» отменяет предыдущий запрос, повторно читает состояние инстанса и запускает очередь. Чаты и черновики сохраняются в памяти текущей вкладки. Для смены токена используется «Выйти» и повторный ввод данных; выход очищает локальную историю. Приложение не авторизует аккаунт и не меняет настройки GREEN-API самостоятельно.

## Формы и общие компоненты

Формы подключения и создания чата используют React Hook Form: проверка при уходе из поля, повторная проверка исправлений после отправки, фокус на первом невалидном поле. Правила нормализации используются и формой, и сервисом. Ошибки полей отображаются рядом с ними; ошибки API остаются на уровне формы. Неудачный запрос не очищает введённые данные. Выход очищает учётные данные.

`common/components/text-field` связывает подпись, подсказку и ошибку через `id`, `aria-describedby` и `aria-invalid`. `button` задаёт общий вид и состояние выполнения. `dialog` использует Radix Dialog для модальности, удержания фокуса и Escape; обёртка возвращает фокус на открывший элемент. Во время запроса закрытие приостановлено, поля доступны для фокуса и копирования. Высота диалога ограничена экраном, длинное содержимое прокручивается.
